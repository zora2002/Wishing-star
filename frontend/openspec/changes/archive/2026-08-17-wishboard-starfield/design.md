## Context

動機見 proposal.md - Why。這份設計的前提條件：

- `GET /api/wishes`（`backend/src/routes/wishes.js`）已經是新到舊排序，這次不需要改後端。
- 現在的前端只在掛載時抓一次願望（`frontend/src/App.jsx`），新建立的願望是靠本地 state 插到陣列最前面；目前完全沒有定期輪詢的機制。
- `frontend/doc/macaron-palette.md` 是核准色票的參考文件（目前 16 色），不是程式碼。
- `frontend/doc/Make a Wish (standalone).html`（連同 `frontend/doc/wishing/` 底下匯出的設計 tokens：`tokens/colors.css`、`tokens/spacing.css`、`tokens/effects.css`、`tokens/typography.css`）是這次視覺改版的參考來源，取代先前只依 `story.png` 手繪稿與對話中零散決定的版本，也取代更早一版「滿版鋪滿視窗」的參考檔案內容。它是純視覺／動畫的原型，用的是 7 則寫死的假資料、CSS `infinite` 無限循環同一顆星星，沒有處理「資料量會持續成長的真實願望清單」這件事——這部分的佇列／輪詢邏輯仍以本檔案先前既有的設計為準。這份參考來源呈現的是**置中卡片式**構圖：星空面板是一張尺寸有上限的卡片（`--card-max-width:640px; --card-max-height:400px; --card-aspect:5/4`），外層頁面背景是深色放射狀漸層（`--sky-page-bg-start:#133447` → `--sky-page-bg-end:#04121a`）；願望輸入表單是星空卡片下方另一張獨立的旋轉便條紙卡片（`--note-bg:#fdf3c7`、`--note-shadow`、`--note-tilt:-1.5deg`）。所有卡片與輸入框都是直角、不帶圓角（`--radius-none:0px`）。使用者已確認版面要改成跟這份更新後的參考來源一致，取代前一版「滿版鋪滿視窗、拿掉卡片外框」的方向。
- 前端是純 React + Vite 的 SPA，除了 React 內建的 hooks，沒有動畫套件或狀態管理套件依賴。

## Goals / Non-Goals

**Goals:**
- 播放順序要是可重播、可預期的：直接依現有 API 回傳的新到舊順序決定，不需要新的後端欄位或端點。
- 輪詢和動畫邏輯不引入新的 npm 套件，維持前端目前極簡的依賴狀態。

**Non-Goals:**
- 不同瀏覽器分頁／訪客之間的畫面同步：每個使用者的天空是各自根據自己收到的輪詢結果算出來的，不保證兩人看到同一顆星星在同一個位置。
- 不處理跨頁面重新整理後保留播放進度：重新整理後佇列會從最新一則願望重新開始。
- 不做即時推播（WebSocket/SSE）：動畫本身就是慢速的，輪詢已經足夠。

## Decisions

**1. 播放佇列在前端 state 管理，不新增 API 形狀。**
在元件 state 裡維護最多 7 個「播放位置」，每個位置要嘛是空的，要嘛存著 `{ wish, color, topOffset, spawnedAt }`。每次輪詢成功後，比對新抓到的（新到舊）願望清單跟佇列目前已知道的內容：還沒出現過的願望視為新願望，插進下一個空出來的位置，排在正在播放中、還沒輪到的舊願望前面。當某顆星星的離場動畫結束，清空該位置，並依「新到舊」順序遞補下一則願望，播完最舊一則後回頭接最新一則。
*考慮過的替代方案*：讓後端直接回傳「接下來要播放的順序」。放棄——現有的新到舊排序已經足夠前端自己算，把純呈現邏輯搬到後端反而增加耦合。

**2. 星星的顏色、垂直位置、旋轉角度在「進場那一刻」決定一次，之後整趟飛行都不變。**
一則願望被排進某個播放位置時，立刻隨機挑一個顏色、一個垂直偏移量、一個旋轉角度（比照參考檔案的 `rotate: Math.random()*360`），存進該位置的 state，整趟飛行沿用同一組值。只有下次同一則願望又輪到播放時，才重新抽一次。
*考慮過的替代方案*：每次 render 都用願望 id 算一個固定的顏色（不存 state）。放棄——使用者確認過顏色是「每次出現隨機」，不是固定綁在某個人身上，所以必須在進場時抽一次並固定住，不能每次重新 render 都重算（那樣飛行途中顏色會閃爍變動）。

**3. 輪詢用遞迴 `setTimeout`，並用 `document.visibilityState` 控制暫停/恢復。**
輪詢實作成會自我排程的 `setTimeout`（不是 `setInterval`）：只有在目前這次 `GET /api/wishes` 請求回應後，才排下一次呼叫。每次排程前檢查 `document.visibilityState`，如果分頁不可見就不發請求、改成排下一次檢查；分頁的 `visibilitychange` 事件觸發且變成可見時恢復。
*考慮過的替代方案*：`setInterval`——放棄，因為請求變慢時會讓多個請求疊在一起，`setTimeout` 天生就不會有這個問題。*考慮過的替代方案*：WebSocket/SSE 即時推播——放棄，這個專案的 API Gateway 是 REST 型態，為了一個裝飾性、慢速的功能另外接一個 WebSocket API 是不成比例的新基礎設施。

**4. 星星色票另外存成一份 JS 常數檔，不直接從文件檔匯入。**
新增 `frontend/src/starPalette.js`（或類似命名），把色碼寫成常數，並把 `frontend/doc/macaron-palette.md` 當成給人看的權威來源，兩邊手動保持一致。色票內容已改為 16 色，對應 `Make a Wish (standalone).html` 裡的 `starColors` 陣列。
*考慮過的替代方案*：建置時解析 markdown 檔案。放棄——固定色碼不值得這樣的複雜度。

**5. 動畫用 CSS 自訂屬性 + `animationend`，不引入動畫套件；飄動時間軸比照參考檔案，但位移方式維持原本設計。**
每顆星星元素用 inline 的 CSS 自訂屬性（垂直偏移、飄動時長等）帶入，飄動效果交給 CSS keyframe 動畫處理；元件監聽星星的 `animationend` 事件，用來判斷該把這個播放位置清空、往下遞補。透明度淡入淡出的時間點（8%／92%）比照參考檔案的 `drift` keyframes；但位移方式維持原本用 `left` 百分比（而不是參考檔案固定的 `translateX(-620px)`），因為百分比位移在不同螢幕寬度下才會正確。也刻意不採用參考檔案的 CSS `animation-iteration-count: infinite`（同一顆星星、同一份資料無限循環）——因為我們的星星要能在每趟飛行結束時換成佇列裡下一則真實願望，用 JS `animationend` 驅動單次飛行＋遞補，才能做到內容持續替換；`infinite` 只適合參考檔案那種固定假資料的展示情境。
*考慮過的替代方案*：用 JS（requestAnimationFrame）或動畫套件驅動。放棄——單純的直線飄動用 CSS keyframe 就夠了，也能維持零額外依賴。

**6. 星星圖形改用四芒星 SVG path，取代文字符號 "✦"。**
比照參考檔案的 sparkle path（`M12 2 L15.53 7.146 L21.51 8.91 ...`），用 `fill`／`stroke` 帶入該位置抽到的顏色。
*考慮過的替代方案*：繼續用 "✦" 文字字符。放棄——視覺效果較粗糙，且跟參考檔案的四芒星形狀不符。

**7. 夜空面板背景改用深藍漸層，取代純黑。**
採用 `linear-gradient(180deg, #0a2233 0%, #0e2a36 55%, #14384a 100%)`，比照參考檔案。
*考慮過的替代方案*：維持純黑 `#000`。放棄——這是本次更新裡使用者明確選擇改用參考檔案漸層的項目之一。

**8. 天際線改用 inline SVG path 呈現剪影，取代 CSS `clip-path` 多邊形。**
直接沿用參考檔案現成的天際線 SVG path 資料（`viewBox="0 0 400 130"`，含 `stroke="#081722" stroke-width="4" stroke-linejoin="round"` 讓剪影邊緣柔化），並疊加參考檔案裡的暖黃色小光點（約 6 個，`#ffdf9c`，隨機分布在天際線區域）與灰色紋理點（skyline path 上的小方點，`#d8dde2`）。
*考慮過的替代方案*：繼續用 `clip-path` 多邊形手調座標重現剪影。放棄——參考檔案已經有現成的 SVG path 資料，直接沿用比重新手調 `clip-path` 座標更準確也更好維護；且燈光點的數量與位置在參考檔案裡本來就是分散、非固定 3 個，不需要另外設計成固定 3 個窗格。

**9. 新增一批純裝飾用的靜態閃爍背景星點，跟願望佇列邏輯無關。**
比照參考檔案的 18 顆 `twinkle` 星點：隨機水平/垂直位置（涵蓋整個面板，不只右側）、隨機大小（1-3px）、隨機閃爍時長與延遲，用 CSS `animation: twinkle ... infinite`（明暗來回，不是位移動畫，用 `infinite` 沒有「替換內容」的問題）。這批星點不對應任何願望資料，純粹是背景氛圍，跟星星播放佇列（`useStarQueue`）完全分開處理。

**10. 送出願望成功後，加上置中的星星綻放動畫回饋。**
比照參考檔案的 `burstStar` keyframes（放大 + `drop-shadow` 發光 + 淡出，約 2.4 秒）。送出成功後先進入「動畫中」狀態，畫面中央播放這個動畫，輸入框內容維持不清空；動畫播放完（約 2.4 秒後）才清空輸入框。這個時機沿用 `WishForm.jsx` 既有的 `submitting` 狀態管理方式，不用另外引入動畫函式庫或 state 管理套件。送出失敗時維持現有行為（不播放動畫、不清空、顯示錯誤）。

**11. 畫面文字統一使用 jsdelivr CDN 上的手寫風字型 `jf-openhuninn-1.1`，不額外載入參考來源裡有引入但沒用到的 Space Grotesk／Fraunces。**
（取代前一版「改用 Google Fonts Huninn」的決定。）透過 `@import url('https://cdn.jsdelivr.net/npm/jf-openhuninn-1.1@1.1/font/jf-openhuninn-1.1.css')` 載入，套用到整個許願牆畫面（星空卡片與便條紙表單），`font-family` 保留 `sans-serif` 作為 fallback。參考來源的 `tokens/typography.css` 額外 `@import` 了 Space Grotesk 與 Fraunces，但其 `readme.md` 明講這兩個字型「loaded but currently unused in the live layout」，因此不跟著引入，避免多餘的外部字型請求。
*考慮過的替代方案*：維持 Google Fonts Huninn。放棄——使用者更新後的參考來源改回 jsdelivr 這個字型來源，且要求依參考來源一致；jsdelivr CDN 若無法連線一樣有 `sans-serif` fallback，風險可接受（見 Risks）。

**12. 懸浮詳情移到星星右側顯示，並拿掉背景卡片，比照參考檔案。**
（取代前一版「維持顯示在星星下方」的決定。）使用者確認要跟參考檔案「一模一樣」，且版面已經改成滿版，水平可用空間遠大於原本 480px 寬的小卡片，星星剛進場（面板右側）時「顯示在右側」被裁到的機率大幅降低，跟參考檔案本身的情況接近。改為 `position:absolute; top:50%; left:100%; transform:translateY(-50%);`，純文字、無背景／無外框，顏色用 `--text`。
*考慮過的替代方案*：維持前一版「星星下方＋卡片背景」的做法。放棄——使用者現在明確要求視覺上跟參考檔案一致，且滿版版面已經讓「右側顯示」的裁切風險大幅降低到可接受範圍（星星剛進場、位置非常靠右緣的極短暫時間內仍可能被裁到一部分，這點參考檔案本身也有同樣的限制，視為可接受的邊界情況）。

**13. 整體版面改為置中卡片式呈現：星空面板與願望輸入表單各自是獨立卡片，不再滿版鋪滿視窗。**
（取代前一版「滿版鋪滿視窗、拿掉卡片外框」的決定。）頁面背景鋪滿 `100vh`，改用深色放射狀漸層 `radial-gradient(ellipse at 50% 0%, #133447 0%, #04121a 70%)`（對應 tokens 的 `--sky-page-bg-start`/`--sky-page-bg-end`）並留白置中；星空面板本身寬高設上限（`max-width:640px; max-height:400px; aspect-ratio:5/4`，對應 `--card-max-width`/`--card-max-height`/`--card-aspect`），沿用決策 7 的深藍線性漸層背景，但不再等於整個頁面。星空面板下方留出間距，接著顯示願望輸入表單卡片（見決策 16）。所有卡片一律直角、不帶圓角（`--radius-none:0px`）。
*考慮過的替代方案*：維持前一版「滿版鋪滿視窗」的做法。放棄——使用者更新的參考來源改回置中卡片式構圖，並附上完整的 design tokens 佐證這是刻意的設計系統調整，因此改依這份參考來源調整。

**14. 新增月亮裝飾，用兩個疊在一起的圓形 SVG 模擬弦月，固定在左上角。**
比照參考檔案：一個大圓（`r=42, fill=#f6dd8e`，暖黃色）疊上一個稍微偏移、同色系深色的圓（`r=34, fill=#0a2233, opacity=0.55`）蓋掉一部分，用重疊而非 SVG mask／clip 的方式做出弦月的視覺效果，實作簡單。固定定位在 `left:6%; top:8%`，純裝飾、不隨願望資料變動。
*考慮過的替代方案*：用 SVG `<mask>` 或 `<clipPath>` 做精確的弦月形狀。放棄——重疊圓形的視覺效果已經跟參考檔案一致，不需要多一層 mask 的複雜度。

**15. 願望輸入框改為上下堆疊排列：願望內容欄位在上（滿版寬、置中對齊），姓名欄位與送出按鈕在下一列，拿掉原本的冒號分隔。**
（取代前一版「姓名:願望同一列、冒號分隔」的做法。）願望內容欄位（對應參考來源 placeholder「make a wish」）寬度撐滿表單卡片、文字置中；姓名欄位（對應參考來源 placeholder「name」）與送出按鈕在下一列，姓名欄位寬度縮窄（約 30%）。兩個欄位都維持底線樣式（`border-bottom:1.5px solid`、透明背景、無外框），底線顏色改用 `--note-rule: rgba(58,47,26,0.35)`、文字顏色改用 `--note-ink: #3a2f1a`（因為輸入框現在位於暖色便條紙卡片上，不是深色夜空背景），字級 14px。
*考慮過的替代方案*：維持姓名:願望同一列＋冒號分隔。放棄——新版參考來源改成上下堆疊、無冒號，使用者要求依參考來源一致。

**16. 願望輸入表單改為獨立的旋轉「便條紙」卡片，取代原本疊加在星空場景下方、透明背景的輸入列。**
表單卡片背景改用暖黃色 `--note-bg:#fdf3c7`，加上陰影 `--note-shadow: 0 6px 16px rgba(0,0,0,0.35)`，套用 `--note-tilt:-1.5deg` 的些微旋轉，直角不帶圓角，呈現手寫便條紙貼在星空照片下方的視覺效果。卡片本身有獨立的內距與最大寬度（`--note-max-width:340px`），置中顯示在星空面板正下方、有間距。
*考慮過的替代方案*：維持透明、疊加在場景底部的輸入列。放棄——新版參考來源改成獨立卡片，使用者要求依參考來源一致。

**17. 送出按鈕圖示改為手繪風紙飛機造型，取代原本的流星圖示；顏色改用固定色碼 `--note-accent:#b8860b`，不沿用 `--accent`。**
比照參考來源的按鈕 SVG path（`M21 3 L3 10.5 L10.5 13.5 L13.5 21 Z` 加一條對角線），描邊風格、無填色。顏色直接採用參考來源的 `--note-accent` 深金色，跟星星／綻放動畫用的 `--accent`（暖米黃 `#ffe9b8`，對應參考來源的 `--burst-glow`）是兩個不同色調，因為按鈕現在位於便條紙卡片上，需要跟便條紙自己的暖色調（`--note-ink`／`--note-rule`）搭配，而不是延續夜空卡片的色調。
*考慮過的替代方案*：沿用流星圖示與 `--accent` 變數統一色調。放棄——使用者要求依參考來源的圖示造型與顏色一致；且新版按鈕位於便條紙卡片而非夜空卡片上，用便條紙自己的色調（深金）在視覺上更協調。

## Risks / Trade-offs

- [不同分頁/訪客看到的星星不一致] → 屬於 Non-Goals 範圍內可接受，天空本來就是各自畫面的裝飾呈現，不是共享同步的畫面。
- [輪詢間隔設太長，會讓新願望感覺很慢才出現] → 調整間隔（見 Open Questions）讓它遠短於一顆星星飛行的時間，感覺上不會拖延。
- [`animationend` 驅動的遞補邏輯，如果動畫被中斷（例如同一元素上又疊加了其他 transition）可能不會正確觸發] → 保持星星元素跟它的容器單純、不加其他 transition，讓 `animationend` 每趟飛行只會觸發一次。
- [色票資料在 `frontend/doc/macaron-palette.md` 和新的 JS 常數檔各存一份，兩邊可能改一邊忘記改另一邊] → 兩邊都只有 16 筆資料，量小；在常數檔開頭加一行註解說明兩者的對應關係。
- [新增 jsdelivr 外部字型依賴，CDN 若無法連線會影響字型顯示] → `font-family` 保留 `sans-serif` fallback，字型載入失敗不影響功能，只影響觀感。

## Migration Plan

純前端變更，後端、API、資料結構都不用動。透過現有的 `deploy-frontend.yml` GitHub Actions workflow，合併到 `main` 後自動建置、同步到 S3、清除 CloudFront 快取，跟其他前端變更的部署方式一樣。回滾就是正常的 revert 後重新部署，不需要跟後端協調。
